## Why this device matters

The GXV3370 adds a genuinely different hardware class to the census: an enterprise IP video phone / desk communications endpoint with an embedded Android application platform.

More importantly, it independently repeats a schema pressure first seen on the Canon C3530i:

```text
real custom-application runtime
  !=
unrestricted application admission
```

The mechanisms differ.

Canon MEAP is package/license/administrator controlled. The GXV3370 is Android-based, but Grandstream still exposes an explicit administrator policy that can allow third-party application install/uninstall, require an administrator password, require administrator authentication for unknown sources, or prohibit install/uninstall.

That makes admission control a repeated cross-vendor pattern rather than a Canon-only oddity.

The GXV3370 also adds a useful recovery distinction: Grandstream documents Safe Mode for isolating problematic third-party applications, factory reset for restoring configuration defaults, and SD-card Recovery Mode for firmware restoration/reconfiguration. Those are different recovery layers and should not be collapsed into one `recovery: true` claim.

## Source 3 — Administrator-controlled application admission

The same Grandstream administration guide has an explicit `Permission to Install/Uninstall Apps` setting.

It documents four meaningful policy outcomes:

```text
Allow
  -> user may install/uninstall third-party apps

Require admin password
  -> administrator authentication is required

Require admin password if app source is unknown
  -> source-sensitive administrator authentication applies

Not allow
  -> user cannot install/uninstall third-party apps
```

The guide separately exposes an unknown-sources control and a Developer Mode toggle.

### Admission truth boundary

This is the key census lesson.

```text
Android application execution exists
  +
application admission policy exists

therefore

custom_code: true
  !=
every acquired unit freely admits arbitrary applications
```

A used unit's current policy, administrator credential state, firmware state and application compatibility remain acquisition/unit facts.

The Developer Mode setting is recorded only as a documented toggle. The evidence packet does not turn that label into a claim of ADB, root, shell, kernel access or bootloader authority.

## Source 4 — Local management and firmware/provisioning paths

The administration guide documents an embedded Web GUI reachable through the phone's IP address. It also documents firmware/configuration provisioning through TFTP, HTTP and HTTPS, direct firmware upload through the Web GUI, and firmware upgrade by external SD card.

This is useful because Grandstream also advertises GDMS cloud device management on the product page. The existence of GDMS does not erase the separately documented local/LAN administration paths.

### Locality truth boundary

The evidence proves local administration and multiple local/LAN firmware/provisioning paths.

It does **not** prove that:

- every SIP deployment works indefinitely without WAN access;
- every third-party application can be installed without internet access;
- every third-party application's runtime is cloud-independent;
- Grandstream/vendor services are optional for every feature;
- the device is `fully_local` in the repo's broader locality model.

For that reason the top-level locality state and vendor-cloud requirements remain `unknown`, while `local_network_operation` is limited to the documented local management surface.

## Source 5 — Factory reset, SD-card Recovery Mode and Safe Mode

Official administration guide:

- https://documentation.grandstream.com/knowledge-base/gxv3370-administration-guide/

Grandstream documents three different recovery layers.

### Factory reset

Factory reset is available from the LCD menu, Web GUI, and hard keys. Grandstream warns that restoring factory defaults deletes phone configuration information. It separately exposes an option to clear the mounted SD card.

The device record therefore marks system configuration as erased for the factory-reset path, but keeps generic user-data and third-party-application impact unknown because the cited section does not define every storage/application consequence.

### SD-card Recovery Mode

When the phone cannot reach the idle screen normally, Grandstream documents Recovery Mode using a FAT32 SD card and a GXV3370 firmware image. The documented procedure installs the system update, restores the device, and restarts it.

The guide does not state exact user/configuration/application data impact for this recovery path, so those fields remain `unknown`.

The guide also explicitly says USB storage firmware upgrade is not supported on the GXV3370. The record therefore does not infer USB recovery merely from the presence of a USB port.

### Safe Mode

Grandstream documents a Safe Mode in which only system applications run. The guide gives the example of entering Safe Mode when an incompatible third-party application makes the phone crash or freeze, then removing that third-party application before returning to normal operation.

This is not firmware recovery. It is an application-level isolation/recovery surface.

That distinction is useful for future matching:

```text
third-party app failure
  -> Safe Mode may isolate/remove app

configuration failure / owner reset goal
  -> factory reset

failed/corrupted software update or no normal idle screen
  -> SD-card Recovery Mode
```

A single positive recovery boolean would hide those different target states and data risks.

## Census lesson

The GXV3370 independently reinforces the admission-control model:

```text
application runtime
  +
administrator admission policy
  +
compatible application
  -> usable custom application surface
```

That same device also shows why recovery should be layered by failure/target state:

```text
Safe Mode
  !=
factory reset
  !=
firmware recovery
```

This is enough to stop treating admission control as a Canon-only edge case. It is still not a reason to freeze a large universal schema: the mechanisms differ, so the repo should preserve the evidence-local structure until more platforms reveal the smallest shared model.
