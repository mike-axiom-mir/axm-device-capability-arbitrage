## Why this device matters

The Roborock S5 is the first mobile robot in the census. It is useful because it stresses several assumptions that camera/router/e-reader records do not:

- the compute surface is physically coupled to motors and a battery;
- local control can replace a vendor cloud;
- persistent custom execution is possible through a documented rooting path;
- recovery quality changes depending on whether the device is still stock or has been modified;
- the original product remains useful as an appliance, so repurposing has an opportunity cost.

The key research result is not merely that "a robot can run code." It is that the S5 demonstrates why recovery needs to be recorded **by device state** rather than as one global yes/no property.

The supported-robots page has a dedicated **Roborock S5** entry. It states that the S5 is sold as:

It also identifies:

- Valetudo binary target: `armv7`;
- rooting method: OTA;
- rooting as a laptop-only path for this model;
- firmware/version caveats for some functions.

### What this proves

- exact-model Valetudo support;
- an ARMv7-compatible Valetudo execution target;
- OTA as the documented S5 rooting family.

### What this does not prove

- exact SoC;
- exact RAM;
- that every individual S5 unit is currently OTA-rootable without checking its recovery firmware state;
- AXM local reproduction.

## Source 2 — Valetudo Roborock rooting/install documentation

URL: https://valetudo.cloud/pages/installation/roborock/  
Source class: mature upstream project documentation  
Checked: 2026-09-13

The Roborock installation guide documents the OTA path as using the robot's normal update mechanism to transfer a customized rooted firmware image. The guide also documents post-root SSH use and setting Valetudo to start automatically after reboot.

The same guide contains an important constraint: newer `miio_client`/recovery firmware can remove the local OTA path, and the exact unit state therefore matters. A factory reset can sometimes restore an older recovery firmware, but units made after the documented cutoff may not regain the local-OTA-capable recovery state.

### What this proves

- persistent custom/root execution exists on supported Roborock models including the S5's listed OTA path;
- SSH is part of the post-root workflow;
- Valetudo can be configured to autostart;
- rooting feasibility is firmware/recovery-state dependent.

### What this does not prove

- SSH on stock firmware;
- universal success on every production date/firmware combination;
- reversible modification.

## Source 3 — Valetudo offline operation

URL: https://valetudo.cloud/pages/faq/  
Source class: upstream documentation  
Checked: 2026-09-13

The FAQ explicitly says Valetudo can be used without an internet connection. It identifies only two Valetudo components that may contact the internet:

- NTP, which can be disabled or pointed at a local server;
- the updater, which only checks GitHub when the user explicitly asks it to.

### What this proves

- the Valetudo control layer is designed for local/offline operation;
- vendor cloud access is not required for normal Valetudo use after provisioning.

### What this does not prove

- that every vendor-firmware background connectivity check disappears;
- that every network feature works on an isolated LAN without any gateway behavior.

## Source 4 — Valetudo local MQTT interface

URL: https://valetudo.cloud/pages/integrations/mqtt/  
Source class: upstream interface documentation  
Checked: 2026-09-13

The MQTT documentation exposes a local home-automation interface with basic robot commands such as start, stop, pause and home, plus telemetry and optional map/capability data.

The same page explicitly warns that some exposed properties are model dependent.

### What this proves

- Valetudo exposes a local machine-facing control/telemetry interface;
- local robot control is not limited to a vendor mobile app.

### What this does not prove

- that every optional MQTT capability is present on the S5;
- raw access to every physical sensor;
- arbitrary low-level motor control.

## Source 5 — Roborock S5 factory reset

URL: https://support.roborock.com/hc/en-us/articles/360035072251-How-do-I-factory-reset-my-Roborock-S5  
Source class: manufacturer documentation  
Checked: 2026-09-13

Roborock documents a physical-button factory-reset process for the S5. The manufacturer states that the process disconnects Wi-Fi and returns the robot firmware to the original factory version.

### What this proves

- a stock-device factory-reset path exists;
- the stock reset includes firmware rollback to the original factory version.

### What this does not prove

- that the same reset restores a Valetudo-rooted device to stock;
- that all post-root partitions/state are recoverable through the stock reset.

## Source 6 — Post-modification irreversibility

URL: https://valetudo.cloud/pages/general/why-not-valetudo/  
Source class: upstream project documentation  
Checked: 2026-09-13

Valetudo's own documentation states that rooting/installing Valetudo is a permanent change and that returning to stock is not available.

This is not a contradiction with Roborock's factory-reset documentation. The two claims describe different device states:

```text
stock S5
  -> manufacturer factory reset can restore original stock firmware

rooted / Valetudo-modified S5
  -> upstream says return to stock is unavailable
```

### Research consequence

A single field such as `factory_reset: true` is insufficient to describe recovery quality. Recovery must preserve **which state the device is in when the recovery path applies**.

## Recovery interpretation

This device exposes an important distinction:

| Device state | Recovery evidence | Meaning |
|---|---|---|
| Stock S5 | Manufacturer factory reset | Documented return to original stock firmware |
| Rooted/Valetudo S5 | Upstream says return to stock unavailable | Persistent modification is effectively irreversible to stock |
| Rooted/Valetudo S5 | Re-flashing/updating rooted image documented | The modified state can be maintained/reprovisioned, but that is not stock recovery |

This distinction should be retained in future device records whenever recovery quality changes after modification.

## Safety / agency note

The S5 is a mobile robot with motors and a battery. This record describes capability on **owned or explicitly authorized hardware** only. The documented execution surface is not permission to control someone else's robot, and general-purpose experimentation should not silently bypass visible user control of physical motion.
